## 状态条识别（HP / MP / EXP）+ 窗口前置
- 结论：不需要手动标注，也**不是**靠 YOLO。三条是固定 UI，直接逐列扫描像素。
- 实测坐标（1366×768，归一化）：红 466-624 / 蓝 634-799 / 黄绿 810-975，都在 y 747-763。
  归一后 hp x 0.3411-0.4568、mp x 0.4641-0.5849、exp x 0.5930-0.7138，y 0.9740-0.9935。
- 算法（server.py `measure_bar`）：ROI 取中间 60% 高度 → 每列算 (S>90 & V>90 & |H-ref|<=30) 的像素比例 → >0.5 视作该列已填充 →
  从左数连续填充列，容忍 <=2 列空洞（条上的高光/数字），断更多就当作空槽。分母用整个 ROI 宽度。
- 关键点：**分母必须是整条槽（含右侧空槽）**。EXP 条绿只占 27.9%，如果只框绿色部分会永远读 100%。
- 色相 ref 在标定那一刻从条左侧 1/4 自动采样并存进 bars.json（hp=1 / mp=101 / exp=33），换皮肤自动适应；
  采样失败退化为纯 S/V 判定，实测两者结果一致（空槽是浅灰 S≈0，天然断得开）。
- 精度：合成图 0/10/25/50/75/90/100% 七档，最大误差 0.5%（整数像素边界）。真实帧与游戏内 (562/566)(181/181)(28.36%) 一致。
- 线程 `bars_loop` 独立于 YOLO，~10Hz；EMA 掉血 alpha=0.9、回血 0.35（掉血要立刻反映）。
- API：`/api/bars`（读配置+实时值）、`POST /api/bars/set`、`POST /api/bars/reset`、`/api/bars/preview`（画 ROI 调试图）。
- 前端：面板顶部三条进度条（<30% 变红字），"标定条"按钮按 hp→mp→exp 顺序拖框，Esc 取消；框用白描边+彩线（纯红框压在红条上看不见）。

## 本地页面"1~2 秒一帧"的真正原因（已修）
- 症状：本地 localhost 看画面像幻灯片，但服务端报采集 31.6 / 推送 30.7，编码 14ms。
- 根因：前端为穿透加的"看门狗 + 逐帧轮询"兜底（1800ms 一张）用 `img.load` 判断 MJPEG
  是否来帧。Chrome 对 multipart/x-mixed-replace 的 `<img>` 不触发/只触发一次 load，
  于是连接正常也被判成"半死"，打开 6 秒后永久切到 1.8 秒一张。
- 顺带假象：`stream_fps` 只在 /stream 生成器循环里更新，没人消费就冻在上次的值，
  所以显示 30.7 骗人。
- 修法：
  1. index.html 删掉 startPoll/stopPoll/scheduleNextPoll/看门狗/lastFrameAt/streamStartAt，
     只留 MJPEG；badge 由 /api/stats 的 tick 维护。
  2. server.py Grabber 加 last_sent_wall（note_sent 里打点），/api/stats 里 sent_age>=1.5s
     就把 stream_fps 报 0。
  3. tick 里遮罩层尺寸兜底：naturalWidth 为 0 时用 /api/stats 的 client_size。
- 实测：curl --max-time 3 /stream?w=1040&q=85 → 90 帧 = 30fps，173KB/帧。
- 教训：MJPEG 的 liveness 不能依赖 img 事件；要判断就用服务端计数（帧时间戳/序号）。

## 跟踪器重写：Kalman + 匈牙利 + ByteTrack（参考开源方案）
- 起因：用户反馈"锁定不住那只怪"，问有没有成熟方案。基线实测（10 秒）：锁定 tid 不变，
  说明当时场景是稳的；真正缺的是运动预测和锁定粘滞。
- 新文件 `webui/track.py`（约 250 行），参考：
  - SORT/DeepSORT：8 维状态 [cx,cy,a,h,vx,vy,va,vh] 匀速卡尔曼，噪声按 h 缩放
  - ByteTrack：高/低分两阶段关联，低分框只补配不新建轨迹
  - OC-SORT：方向一致性代价（inertia=0.2）
  - scipy.linear_sum_assignment 全局最优匹配
- 关键坑（写进代码注释）：
  1. **cv2.KalmanFilter.predict() 只写 statePre，不推进 statePost**。不同步的话每帧都从
     上次校正点外推一格，漏检时框原地不动，等于没有预测。必须 statePost = pred、errorCovPost = errorCovPre。
  2. 漏检不能一直按速度外推：方向一变就飘走。改成前 3 帧外推、之后停在 last_box。
  3. 匹配门限 match_thresh 0.8→0.9（IoU>=0.1 可配）反而更稳：决定匹配的是全局最优+方向，
     不是单个 IoU 大小。min_hits 3→2 显著降低丢帧。inertia 调大反而大幅变差（方向约束过强）。
- 参数（webui/track.py 默认）：high 0.30 / low 0.10 / new 0.30 / match 0.90 / age 15 / min_hits 2。
- server.py：推理 conf 从 DETECT_CONF 0.35 降到 LOW_DETECT_CONF 0.10，给 ByteTrack 第二阶段用；
  界面上的框仍是确认过的轨迹，噪声不会冒出来。
- pick_lock 改成四级：延续 → 就近接回（3 秒内，lock_box/lock_ts）→ 面积×置信度 → 最高置信度。
- 实测：合成密集场景换 ID 214→158、丢帧持平；真实 20 秒锁定 0 次丢失、切换 2 次。

## 「冒出来一两帧就消失」的根因与修法（显示稳定）
- 根因：判定"已识别"只看 conf >= 门限 + 跟踪器 confirmed，而 confirmed = 连续命中 2 帧
  （min_hits=2）。误检连着两帧拿 0.7 就会被画出来，然后消失。置信度过滤没错，缺的是
  "显示端最短驻留/入场门槛"。
- 新增 server.py `pick_visible(tracks, shown, now, show_conf, show_hits, prev_tid)`（抽成独立
  函数，方便用合成序列单测，不进图形界面）：
  1) 首次出现要求 `hits >= show_hits`（默认 4，UI 可调 1~12）；
  2) 出现后 `DISPLAY_MIN_SHOW=0.45s` 内允许 conf 掉到门限下仍继续画（recent 依据 rec["ok"]，

## 显示门限改硬约束（用户反馈「为什么还有 0.49」）
- 现象：门限设 0.60，画面仍出现 `#671 Stump 0.49`，同一只怪还叠着另一个 0.90 的框。
- 根因两条：
  1) `DISPLAY_MIN_SHOW=0.45s` 的按秒宽限 —— 已显示的轨迹掉分后还能挂 0.45 秒低分读数；
     `LOCK_CONF_GRACE=0.08` 又让锁定目标允许 0.52 这种低于门限的值显示。
  2) 同一只怪被两条轨迹重复框住（检测端 dedupe 只对「同类名」生效，模型把同一只怪
     认成两种怪时两个框都活下来，各跟一条轨迹）。
- 改法（commit 3f4c1d5）：
  - 宽限改成按帧数：`DISPLAY_WEAK_MAX=2`（连续低分 2 帧后撤框），删 `DISPLAY_MIN_SHOW`；
  - 删 `LOCK_CONF_GRACE`，锁定不再有置信度滞回（锁定连续性靠 `lock_box` + 3 秒就近接回）；
  - `pick_visible` 末尾对 vis 做重复轨迹抑制：IoU > `DUP_TRACK_IOU=0.55` 只留一条
    （锁定优先，其次 conf 高）；sort 后贪心保留；
  - `dedupe_dets` 加 `dup_thr=0.85`：不同类名但框几乎重合也判重复。
- 合成测试（.tmpchk/gate_test.py，未入库）：0.90→0.49 只画 2 帧；从未达标的 0.49 不画；
  锁定 0.55 也只 2 帧；同框重复轨迹每帧 1 条；两只分开的怪仍是 2 条。
- 注意：服务无 reload，改动需重启才生效（用户自己起服务）。

## 人物定位重写：白字掩码 + CCOEFF（commit 8f22185）
用户反馈「人物匹配非常不准」，用他给的真实截图（1368×800）+ 名字牌图（56×20）复现。

- 原方案为什么不行（实测数据）：
  - 灰度 CCOEFF：模板背景均值 19、画面里同一块 136 → 真身峰 0.743，误检 0.640，差 0.1；
  - 边缘图：地面石块/木纹边缘一样密，peak 0.743 但误检 0.640；
  - 匹配峰只有 1px 宽（x=629 得 0.743，x=630 得 0.437）→ 亚像素错位就腰斩。
- 最终方案：
  1. 帧白字图 = 顶帽(原图 - 3×3 开运算)，只留 1~2px 细亮笔画，背景免疫；
  2. 模板按白字外接框裁紧（56×20 → 56×17，去掉 3 行纯背景）；
  3. 两边高斯 σ=1.0 → 峰从 1px 尖峰变成 ±2px 平台，真身 0.958；
  4. 两边各加 0.02 底噪 → 用 TM_CCOEFF_NORMED。
- 两个必须记住的数值陷阱：
  - TM_CCORR_NORMED 在白字图上，模板缩到 20px 宽时**纯噪声都能得 0.95**
    （能量小 → 归一化分母小），不能只看分数；
  - TM_CCOEFF_NORMED 对全黑窗口（方差≈0）会除出 **1.000 假峰**，top5 全是 1.000
    而真身 0.958 排不上；加 0.02 底噪后假峰全退到 0。
- 三级搜索：局部 ±60 → ±200 → 全图 top5。局部优先的真正原因是**画面左下角 LV 栏
  印着同一个名字（0.84）**，全图直搜会一直抢，人物出画面就把框甩到左下角。
  HUD 区（底 7%/顶 5%/左右 9%）额外扣 0.12，判定用扣完的分，显示用原始分。
- 尺度扫描：只能全分辨率扫 0.40~1.60。半分辨率下模板只剩十几像素，0.5 和 0.32
  分数一样，扫出来的尺度全错（曾因此把 scale 存成 0.88 把模板缩坏）。
- 上传整张截图要拒绝（白字铺满全图 → 模板 = 整屏文字布局）。
- 实测：真身 0.958 / UI 同名 0.840 / 纯噪声 0.43；合成 120 帧 120/120 成功、
  误差 0px；局部 0.8ms/帧、全图 18ms、尺度扫描 0.6s（仅上传/重标）。
