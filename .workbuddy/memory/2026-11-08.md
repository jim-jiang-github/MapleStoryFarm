## 状态条识别（HP / MP / EXP）+ 窗口前置
- 结论：不需要手动标注，也**不是**靠 YOLO。三条是固定 UI，直接逐列扫描像素。
- 实测坐标（1366×768，归一化）：红 466-624 / 蓝 634-799 / 黄绿 810-975，都在 y 747-763。
  归一后 hp x 0.3411-0.4568、mp x 0.4641-0.5849、exp x 0.5930-0.7138，y 0.9740-0.9935。
- 算法（server.py `measure_bar`）：ROI 取中间 60% 高度 → 每列算 (S>90 & V>90 & |H-ref|<=30) 的像素比例 → >0.5 视作该列已填充 →
  从左数连续填充列，容忍 <=2 列空洞（条上的高光/数字），断更多就当作空槽。分母用整个 ROI 宽度。
- 关键点：**分母必须是整条槽（含右侧空槽）**。EXP 条绿只占 27.9%，如果只框绿色部分会永远读 100%。
- 色相 ref 在标定那一刻从条左侧 1/4 自动采样并存进 bars.json（hp=1 / mp=101 / exp=33），换皮肤自动适应；
  采样失败退化为纯 S/V 判定，实测两者结果一致（空槽是浅灰 S≈0，天然断得开）。
- 精度：合成图 0/10/25/50/75/90/100% 七档，最大误差 0.5%（整数像素边界）。真实帧与游戏内 (562/566)(181/181)(28.36%) 一致。
- 线程 `bars_loop` 独立于 YOLO，~10Hz；EMA 掉血 alpha=0.9、回血 0.35（掉血要立刻反映）。
- API：`/api/bars`（读配置+实时值）、`POST /api/bars/set`、`POST /api/bars/reset`、`/api/bars/preview`（画 ROI 调试图）。
- 前端：面板顶部三条进度条（<30% 变红字），"标定条"按钮按 hp→mp→exp 顺序拖框，Esc 取消；框用白描边+彩线（纯红框压在红条上看不见）。

## 外网画面改 H.264(fMP4+MSE) 直播 + 隧道优选（提交 175ab36）
- 用户：「外网简直看不了，能不能用视频编码」「moonlight 那种串流」。
- Moonlight 那套（NVENC + GameStream 私有协议 + 原生客户端 + UDP）浏览器用不了，
  且本机无 NVIDIA 卡。浏览器能落地的是「H.264 低延迟编码 + MSE」，这轮就按这个做。
- 关键实测数据（决定方案）：
  · tunnelmole：单次请求往返 0.7~3s（偶发 26s），**MJPEG 长连接 10s 内 0 字节**（整段缓冲），
    一条 /stream 还会把整条隧道堵死。
  · cloudflared quick tunnel（Cloudflare 边缘/lax13）：往返 0.3~0.8s，**长连接可以流式**。
  · 隧道吞吐只有 110~200 KB/s ≈ 1 Mbps —— 2200k 码率必然播不动（实测 0.5 倍速播放）。
- 所以：ffmpeg libx264 baseline@L4.0 / ultrafast / zerolatency / gop=fps*0.5，
  每 0.5s 一个 moof+mdat 分片；前端 MediaSource。双通道：
  /video/live（单连接连续推流，cloudflared 下用）＋ /video/seg（短请求逐片，tunnelmole 兜底），
  6s 拿不到数据自动降级，最后兜底逐帧 JPEG。
- 前端自写 ISO-BMFF 切分器：隧道 chunk 边界随机，先拼成完整 moof+mdat 再 appendBuffer。
- 画质档位：流畅 450k/800px/12fps、标准 900k/1000px/15fps（默认）、高清 1600k/1200px/20fps。
  900k 下 cloudflared 实测能持续实时播放（dt≈2.4s/2.5s，readyState 多数为 4）。
- 依赖：pip install imageio-ffmpeg（自带 ffmpeg 9.0.2，含 libx264；不用下 50MB 独立 exe）。
- cloudflared.exe 经 ghfast.top 镜像下载（~80KB/s，断点续传两次才下完 52.8MB），
  放 tools/bin/（tools/bin/.gitignore 排除，不入库）；首次运行会弹 Windows 防火墙提示。
- tools/tunnel.py：打印「带 ?k=口令 的完整网址」+ 写剪贴板；优先 cloudflared，退回 tunnelmole。

## 手机端卡顿定位与优化（14:20 起，commit 8f9ff9d）
- 用户反馈「手机上看很卡、帧率很低」。实测隧道：cloudflared quick tunnel 同一连接
  往返 0.47~1.0s、吞吐 ~1.2Mbps（上传到 CF 边缘实测 5~12Mbps，瓶颈不在家宽）。
- 判断根因两条：① iPhone Safari 没有 MSE，旧逻辑直接退回逐帧 JPEG → 1 帧/秒幻灯片；
  ② 编码参数浪费比特：0.5s 一个 I 帧（每 7 帧重画）+ baseline 无 CABAC。
- 编码实测（真实画面 36 帧，900k）：旧 1177kbps/PSNR 27.8 → 新 897kbps/PSNR 33.0。
  新参数：veryfast + tune animation + main(avc1.4D4028) + GOP=1s + -threads 2
  （默认按核数开 30 帧线程会把输出滞后 ~1s）。
- 新增 iOS 原生 HLS：/video/hls/index.m3u8 + init.mp4 + seg_{seq}.m4s，
  2 个 1s 分片拼成 2s 一段（HLS_GROUP=2），因为高 RTT 下 1s 段拉不完。
- 服务改监听 0.0.0.0，启动脚本/隧道脚本打印「手机同 WiFi」局域网地址；127.0.0.1 免口令。
- 起播 15s 内不计卡顿降档；追直播点阈值 1.2s → 2.5s。
- 页面新增「画面通道」行（H.264 直播 / HLS 原生），便于下次远程判断走的哪条路。
- 结论已写进 README：想真正像本地一样顺，只能走局域网或 VPS frp/端口映射，
  免费隧道 1s 往返的天花板压不下去。

## 「比之前更卡」定位（15:30，commit 694ddcc）
- 两个真因：① 分片通道 URL 拼成 `/video/seg?i=96?w=640`（videoQuery 自带 "?"），
