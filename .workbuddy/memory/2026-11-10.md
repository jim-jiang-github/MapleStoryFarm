
## 技能框编辑三连修（7048d3f）

用户实测反馈三问题 → 修复方案（后续改技能编辑时别走回头路）：

1. **确认收尾**：编辑中「画面调整」按钮变「✓ 完成」（高亮），点击/Esc 收起
   并 toast 已保存范围值；画面顶部常驻操作提示条。
2. **实时跟随**：锚点=人物身体中心实时值（rAF 循环重绘 drawMasks），
   拖动那一会儿冻结在 pointerdown 时刻（drag.anchor）防框漂移；
   没定位到人物 → 画面中心偏下 (W/2, H*0.62) 兜底，照样能编辑。
   关键函数：skillAnchorLive / skillAnchorNow / skillLoop。
3. **显式方向 dir**：both 左右 / front 身前 / left 仅左 / right 仅右。
   skill_rects 用 _dir_extents 裁半边；one_sided 改读 dir（不再靠框形状猜）；
   旧 range_side=front 迁移进 dir。front=感知两侧+出手前转身对正；
   left/right=另一边的怪压根不进判定（走路目标也只认活动半边的带）。
   server 画框：front 只画当前朝向半边带 -> / <- / ? 箭头。
   编辑画面：锚点竖虚线分界、不活动半边压暗、front 两侧标
   「朝左/朝右时打这边」。

测试：test_bot 107/107，test_headless 66/66（新增仅右/身前两条方向用例）。
用户 botconf.json 里的 skills 是他实测拖出来的（左37右163 不对称），一起提交。

## 技能方向收敛为两种（5e24f40）

用户澄清：**没有固定只打左/右的技能**，只有两种——
- both 以人物为中心的全方位（框内两边都打）
- front 身前单向（只能打人物面前，**技能框必须跟着人物转向翻**）

要点：
- dir 只剩 both/front；旧值 left/right 读取时自动并成 front
- 感知框恒为整框（front 也两侧都感知），front 靠出手前转身对正保证只打身前
- server 画框：front 只画当前朝向那半边 + -> / <- 箭头，转身立刻翻
- 前端编辑画面：锚点竖虚线分界 + 两侧「朝左/朝右时打这边」，
  从 bot 状态实时取 face（pollBot 里 lastFace）压暗不打的半边

## 身前技能框跟朝向翻——位移观测（dbd3e12）

用户实测：手动移动/转向人物，橙色 SK 框僵在一边不翻。根因：`_face` 只在
bot 自己发按键（转身/走路/巡逻）时更新，玩家手动操作 bot 感知不到。

修法：`_watch_face` 每轮对比人物身体中心相对锚点的累计位移，往一边挪过
`MOVE_FACE_PX`(10px) 就判定朝那边并移动锚点。覆盖手动走/被击退/bot 巡逻；
匹配抖动 ±几像素凑不够阈值不会误翻。四处朝向复位统一走 `_reset_face()`
（顺带清锚点）；挂机关着（_loop 停止分支）也继续观测，纯手动看框照样翻。

注意：原地转身不产生位移，检测不到（极边缘情况；front 技能出手前
本就会重新对正，不影响打）。测试：test_bot 114/114（[26] 位移观测）、
test_headless 68/68（合成画面挪人物 → face 翻面，走真实模板跟踪链路）。

## 技能框"消失"的两条根因（ded642f）

用户截图「技能框都没了」，复现后确认是两件事叠加：

1. **身前技能朝左塌成窄条**：`左30 右170` 的框是按朝右量的形态，老代码
   朝左时按「只留左半边」裁 → 只剩 30px 宽，看着像没了。
   正确语义 = **整体镜像**：朝左时 [左,右] 翻成 [右,左]，形状不变。
   `skill_rects(skill, char_box, face)` 一个函数管换算：face<0 镜像、
   face=0（决策阶段）横向 max(左,右) 对称展开当感知。server 画框直接
   调它——画的和打的永远同一份。
2. **挂机关着画灰色 1px** → 岩石背景上等于隐形。改成暗一档的橙
   `BOT_RANGE_OFF=(0,140,210)`。以后不要再把"关=灰"当省事做法。

前端编辑画面：虚线灰框 = 镜像后的位置，标「朝右时（现在调的）/
朝左时（镜像）」；别再用"压暗半边 / 朝左朝右打这边"那套旧语义。

教训：**改绘制效果必须实机截图验证**。`try/except: pass` 包着的画框
不出错但可以"看不见"，单元测试抓不到，得靠 test_headless 的画框回归
（量非背景像素 span：朝左宽仍≈200 且整体在左、关着也可见）。

## 人物识别不到 → 默认画面正中心（395af16）

- `bot.center_char_box(w,h)`：画面中心的假名字牌框（只保证身体中心在画面
  中心，牌子高矮无所谓——决策/画框对 char 框只用得到身体中心）。
- `_bot_state` 多返回 `size`（grabber.client_size，窗口丢了是 None）；
  bot 丢人时拿 size 造中心锚点继续打，size 也没有才走老停手逻辑。
- 坑：合成锚点下**不能每帧 _reset_face**——face 永远 0 → `face != side`
  每帧都转身、永远打不出手。改成 `self._synth` 标记只在真→假切换那帧
  作废一次（顺带清观测锚点，找回真人时中心→真人的跳变不会被当位移翻面）。
- `overlay_char` 丢人时 ME 不画（不造假分数），技能框照画、锚点同 bot。
- 前端 `skillAnchorLive` 兜底从 H*0.62 改成 H/2，和后端对齐。
- 测试：test_bot 126/126（新增 [27]/[27b]），test_headless 76/76
  （新增丢人端到端 + 画框锚中心回归）。

## 人物框消失的真因：匹配尺度死结（bf57077）

- 现象：人物在画面里、模板也在，就是不出 ME 框；`/api/char` 显示
  score≈0.6 < thresh 0.8、scale 恒为 1.0。
- 根因链：名字牌像素尺寸 ∝ 游戏窗口宽度。模板是 1366 窗口下截的（55px），
  当前客户区 2049 → 名字牌约 82px，需要 scale≈1.49。而 `_auto_recalibrate`
  只认「frame_size 变了」，frame_size 又只存内存：重启后第一次进来只记尺寸
  就 return，从此永远认为没变过 → 尺度卡死，等多久都不会好。
- 另外扫描范围上限 1.62，窗口 1.5 倍只能勉强够到，再大必挂。
- 修法：charconf 存 `calib_w`；宽度一变按比例算尺度并**用当前帧验证**
  （分数过门限才采纳）；没有 calib_w 的老配置退回全尺度扫描（门槛
  max(0.88, thresh)、最多 3 次）；扫描范围放到 0.30~3.00。
- 新增 `POST /api/char/recalibrate` + 面板「重标尺度」按钮救急。
- 诊断手法（以后复用）：/api/char 看 score/scale → 拉 template.png 和
  /api/snapshot 用 matchTemplate 扫尺度，一眼看出模板实际需要几倍。
  注意帧被别的窗口盖住时 snapshot 是白的，score 也是假的。

## 名字牌尺度为什么是 1.5 倍：游戏是 DPI-unaware（实测查清）

- `Maplestory_Classic.exe` 进程 DPI 感知 = **unaware**（`GetProcessDpiAwareness`
  实测，对比 explorer.exe 是 per-monitor）。系统缩放 150%，物理屏 2560×1600，
  逻辑 1707×1067。
- 链路：游戏内部按 1366×768 渲染 → Windows 把整幅位图**拉伸 1.5 倍** →
  占 2049×1152 物理像素（1366×1.5=2049，就是 server.py 注释里那对数字）。
  名字牌物理像素 54 → 81，而且是被双线性拉糊的。
- 我们自己是 per-monitor v2 aware → mss 抓物理像素、坐标不会错位；但看到的是
  被放大的画面 → 模板尺度必须 ×1.5，否则 score 卡在 0.6 < 0.8 门限。
- **RDP 会改缩放/分辨率**：换客户端（各自 DPI 不同）、mstsc 拉窗口、断开重连，
  会话缩放或分辨率都会变 → 游戏物理窗口尺寸变 → 名字牌尺寸变。所以 1.5 不是
  恒定值，会随远程会话漂。calib_w 的宽度比例自愈正好覆盖（缩放变 = 物理宽度
  按同比例变），验证过：150%↔100% 时比例算出 1.5↔1.0。
- 想让尺度恒定 + 画面清晰：给 exe 设「属性→兼容性→更改高 DPI 设置→替代高 DPI
  缩放行为=应用程序」，游戏自己按物理像素渲染就不再被拉伸；或固定窗口化尺寸。
- 诊断套路（下次直接抄）：`GetProcessDpiAwareness(游戏pid)` 看 aware 级别 +
  `mss.monitors` 看物理分辨率 + `GetSystemMetrics(0)`（unaware 下）看逻辑分辨率，
  三者一比就知道有没有被虚拟化/拉伸。
- 顺带修正 server.py 顶部那条注释：原文「1366x768 被报成 2049x1152」方向写反了，
  实际是物理 2049×1152 被 unaware 进程报成 1366×768。
