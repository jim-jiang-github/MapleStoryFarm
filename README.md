# MapleStoryFarm

冒险岛怀旧服挂机 + 预览 WebUI（抓屏 → YOLO 检测 → 网页实时预览 / 血蓝经验条读数）。

## 本地预览

```
启动预览.bat            # 或  python webui/server.py --open
```

默认 http://127.0.0.1:8765 。本地直连走 MJPEG（最省 CPU），画面、检测框、状态条读数都在同一个页面里。

**改完代码要重启服务。** `index.html` 是每次请求现读磁盘的，`server.py` 的路由却是启动时定下的，所以很容易撞上"页面已经是新的、接口还是旧的"：新按钮点了没反应、控制台报 `Cannot read properties of undefined`。判断方法很简单——`curl 127.0.0.1:8765/api/bot`，返回 404 就是进程没重启。前端现在会把这种情况直接写成「服务在跑旧代码，重启后可用」。

## 外网访问

```
外网访问.bat
```

脚本会做三件事：

1. 带口令（默认 `msfarm2026`）启动预览服务；
2. 起一条免注册隧道，**优先 cloudflared**，没有就退回 tunnelmole；
3. 把 `https://xxxx/m?k=口令`（手机页）打出来并复制到剪贴板 —— 手机加到主屏幕就能用。

口令不带 `?k=` 打不开；打开过一次浏览器记 7 天，不用每次输。

### 为什么优先 cloudflared

| | cloudflared（quick tunnel） | tunnelmole |
|---|---|---|
| 转发方式 | Cloudflare 边缘，HTTP/2 流式 | 中转节点，会**整段缓冲**长连接 |
| 单次往返 | 0.3~0.8s | 0.7~3s（偶发十几秒） |
| 装法 | 把 `cloudflared.exe` 丢进 `tools\bin\` 即可（脚本自动发现） | `npx` 自动下载，免安装 |

> cloudflared 首次运行 Windows 会弹防火墙提示，点 **Allow** 就行（它只往外连，不开本地端口）。

## 两个页面，各管各的

| | 本地页面 `/` | 手机页 `/m` |
|---|---|---|
| 给谁 | 坐在电脑前调东西 | 在外面瞄一眼 |
| 画面 | MJPEG 实时流（局域网一样流畅） | 640px 缩略图，2 秒一张 |
| 流量 | 局域网随便跑；隧道撑不住 | 约 50 kbps，20 MB/小时 |
| 功能 | 识别开关、精度/速度、定位框、**屏蔽区编辑** | 状态大字 + 缩略图 + 血蓝经验 + 动静折线 |

**公网打开 `/` 会自动跳到 `/m`**：隧道会把 MJPEG 长连接整段憋住，主页面在公网上
只会是一片黑，不如直接去手机页。真要强开加 `?full=1`。

编辑（屏蔽区）本来就该在本地做 —— 拖框需要实时反馈，穿隧道的画面上根本拖不准。

三条状态条默认自动定位、画面上默认画出定位框（白框=判定区，洋红框=整条槽，
黄竖线=填充终点），平时不用管；只有自动定位失效、需要手动框坐标时，才在地址后面
加 `?cal=1` 放出「标定条 / 自动定位」两个按钮。

### 本地面画为什么不经 ffmpeg

本地和局域网走的是 MJPEG：每帧一张独立 JPEG，浏览器收到就画，没有编码器排队，
所以延迟只有十几毫秒。代价是带宽大，但本地链路不在乎。

之前卡的原因是"每帧太大"：服务端不论前端显示多大，都按 1366×768 原图编码，
每帧 200~300KB、26fps ≈ 7.8MB/s。浏览器每帧都要完整解一次 JPEG，本机同时跑
游戏和 YOLO 时解码就掉帧，看着一顿一顿。现在：

- 前端按画面上真正占的像素（一般 1000~1200px）请求 `/stream?w=1200&q=85`；
- 帧调度改成"按目标时间戳补差"，不再把编码耗时白搭进去 → 26fps → **30fps**；
- 编码放到线程里跑，不再阻塞事件循环（血条/统计请求不用排队）。

实测每帧 156KB、30.0fps、帧间隔中位 33ms、画面延迟 14ms，体积比原来小一半。

### 为什么砍掉了 H.264

之前为了"外网也能看实时画面"上过一整套 H.264：ffmpeg 编码 → fMP4 分片 → MSE / HLS 播放。
折腾很久，结论是**免费隧道的物理上限压不下去**：

| 指标 | 实测 |
|---|---|
| cloudflared quick tunnel 单请求固定往返 | **1.1~1.6 秒**（压不下去的成本） |
| 有效吞吐 | 200 kbps ~ 1.2 Mbps（同一节点一天之内就能掉这么多） |
| 家宽上行到 CF 边缘 | 6~9 Mbps（不是瓶颈） |
| 900k 码流 + 2 秒分片 | 拉一段要 2 秒 → 追不上，必然周期性卡死 |

也就是说：链路好的时候码流能跑，链路一抖就卡，而链路抖动你控制不了。
既然需求只是"在外面看一眼挂机有没有在动"，就没必要跟这个上限较劲了 ——
一张 12 KB 的缩略图在 200 kbps 上有 4 倍余量，永远看得动。

代码上已经把 video.py、`/video/*`、画质档位、测速端点全部删掉，只留 MJPEG + 手机页。

### 免费隧道的替代方案

如果哪天真的需要"在外面也像本地一样顺"：

1. 手机和电脑同一个 WiFi → 用局域网地址（往返几毫秒）；
2. [Tailscale](https://tailscale.com/)（免费，P2P 打洞，能跑满你那 6~9 Mbps 上行）；
3. 路由器把 8765 端口映射出去，或自己的 VPS 跑 frp。

## 目标跟踪与锁定

`webui/track.py`，不引入新依赖（numpy / OpenCV / scipy 都是已有环境）。

用的是公开方案里现成的组合，没有自己发明：

| 借鉴 | 用在哪 |
|---|---|
| **SORT / DeepSORT** | 8 维状态 `[cx, cy, a, h, vx, vy, va, vh]` 的匀速卡尔曼，噪声按目标高度缩放 |
| **ByteTrack**（ECCV 2022） | 两阶段关联：先用高分框配，再用低分框给落空的轨迹补配一次；`track_buffer` 内保留丢失轨迹 |
| **OC-SORT**（CVPR 2023） | 关联代价里加「速度方向一致性」，惩罚方向突变，减少交叉时换 ID |
| **匈牙利算法** | 用 `scipy.optimize.linear_sum_assignment` 做全局最优匹配，替代原来的逐对贪心 |

原来的做法是「IoU 贪心 + 最近距离兜底 + EMA 平滑」，三个硬伤：贪心会一错连累后面、距离兜底没有方向约束（旁边的同类怪会被抢走）、漏检时框停在原地不动。

**锁定策略**（`pick_lock`）分四级：延续上一帧 → 按最后位置就近接回同类（3 秒内）→ 面积×置信度 → 置信度最高。第二级是关键：目标被遮挡或跑出画面边缘再回来时，接回原来那只，而不是跳到画面里最大的一只。

实测（合成场景，6 只同类怪密集游走、10% 漏检、检测框抖动 4px）：换 ID 从 214 次降到 158 次，丢帧持平；单目标常规场景持平。真实环境 20 秒采样：锁定从未断过，切换 2 次。

**显示门限**（面板上的「识别阈值」滑块，`/api/detect/conf?v=0.6`）：低于门限的框不画、不计数、不参与锁定，默认 0.60。拖动即时生效，值存在 `webui/detconf.json`。

它和推理阈值是两件事：送进模型的 `conf` 是 0.10（`LOW_DETECT_CONF`），低分框只用来给落空轨迹补配一次，所以轨迹不会因为一两帧掉分就断；显示门限只决定「什么算识别到」。门限对显示是硬约束：这一帧量测到的分数低于门限就不画，不按秒、也不按帧给宽限（曾经有过 0.45 秒和 2 帧两种宽限，结果是分数在门限附近横跳的轨迹几乎一直挂着 0.58 的框，看上去像门限没生效，已全部去掉）。

**稳定帧数**（`/api/detect/stability?v=4`，面板第二个滑块）：置信度高不等于目标真实，误检偶尔也能连着两帧拿到 0.7。所以显示端还有几道闸（`pick_visible`）：

1. 这一帧量测分数低于门限 —— 直接不画。画出来的框，标签上的数字恒 ≥ 门限；
2. 累计命中达到 `show_hits` 帧才允许第一次出现（默认 4 帧，约 0.15~0.2 秒）；
3. 连续 2 帧没观测到就不再画（`DISPLAY_MAX_MISS`），不留停在原地的幽灵框。这类漏检帧用卡尔曼预测的位置 + 上一次达标的分数，所以数字仍然 ≥ 门限；
4. 同一只怪被两条轨迹重复框住（IoU > `DUP_TRACK_IOU`）时只画一条，锁定优先、其次置信度高者。检测端的 `dedupe_dets` 也会把「不同类名但框几乎重合」的两个检测当重复去掉。

跟踪器内部不受影响，仍按 `max_age` 保留轨迹，随时能接回。合成序列验证：0.90 掉到 0.49 当帧即消失；0.61/0.59 交替时只画 0.61 那几帧；漏检 2 帧不闪、第 3 帧撤框；连续 2/3 帧的误检完全不显示。

### 检测频率（`/api/detect/fps?v=N`）

面板下拉「检测频率」，`0` = 不限（跑满），否则 5~30，存 `webui/detconf.json`。

先说清楚它**不是**什么：它不改变单帧耗时。YOLO 的 `imgsz` 是固定的，图多大多小都要 letterbox 到同一张张量上跑，网络前向的计算量一分不变。实测（1366×768，fast 模式）：

| 动作 | 耗时 |
|---|---|
| `frame.copy()` | 0.86 ms |
| 拷贝 + 涂 5 个 UI 排除区 | 1.18 ms（涂灰本身 0.32 ms） |
| predict 全帧 | 66.3 ms |
| predict 裁掉底部 14%（模拟大块排除区） | 62.7 ms |

也就是说**屏蔽区省不出算力**：裁掉 14% 的像素只快 3.65 ms（5.5%），省的全是预处理 resize。同样的道理，「识别完再过滤」也不会更快——它只会白跑一遍。真要省，只能动两处：**降 `imgsz`**（`MODES` 里 fast 384×672 / accurate 544×960）或**降频率**（这个开关）。频率降到 10，检测线程的 CPU 就剩原来的三分之二左右，而画面上的框本来就只在每次推理后刷新一次，看上去几乎没差别。

实现上有个坑值得记：不要用「上次睡完的时刻」当基准去算下一帧该睡多久。Windows 的 `time.sleep` 精度约 15.6 ms，每睡一次都可能多睡一格，这点误差会一帧一帧累加——初版就是这么写的，设 15 实际只能跑到 7.9。现在按「下一帧的计划时刻」（`det_state["next_infer"]`）推进，每帧给计划时刻加上 `1/N` 秒而不是加实际耗时，多睡的那格下一帧少睡一点就补回来了；推理本身比 `period` 还慢时直接以当前时刻重新起算，不攒欠账。实测（双实例抢 CPU、地板 10.2 FPS）：设 8 跑到 8.0/8.1，设 10 及以上受地板限制不超 10.2。刹车期间既不抓帧也不跑跟踪器，画面保持上一次的标注。

## 自动打怪（挂机）

面板上的「挂机: 开」按钮，参数在下面几行。逻辑在 `webui/bot.py`，只管「什么时候按哪个键」；识别、跟踪、血条都还是 server.py 那套，通过回调把状态喂进去。

| 键 | 干什么 |
|---|---|
| Ctrl | 攻击 |
| Alt | 跳跃（目前没用上，先留着） |
| ←/→ | 走位、转身 |
| 8 / 9 / 0 | 喝药（面板上选一个，默认 8） |
| Z | 拾取（全程无脑按） |

每 20ms 一轮，优先级：**血低喝药 → 拾取 → 打范围内的怪 → 走向范围外的怪 → 没怪就左右巡逻**。

- **喝药**：血低于「血线」（默认 60%）按一次，两次之间至少隔「喝药间隔」（默认 3 秒）。血量读不到（血条没标定）时一下都不会按，不蒙着眼睛喝药。
- **攻击距离**（默认 160px）：人物中心到怪物中心的**水平**距离。距离内先站住、转向目标、等朝向生效、再按「攻击间隔」（默认 420ms）攻击。画面上会实时画出这条范围带（左右两条竖线 + 上下虚线 + `ATK 160px` 标签），灰色=挂机关着（方便调距离），橙黄=在跑。
- **纵向容差** 150px：只打同一层的怪。这个游戏只能左右走，上下层的怪够不着，把它们算成目标只会让角色对着空气挥刀。
- **巡逻**：视野里没怪就左右来回走，2.5 秒换一次方向；关掉就站在原地等。

为什么攻击前要先「转向」：这个游戏的普攻只打正面，站着不动直接按 Ctrl 可能打的是背后。转身只能靠按方向键，所以轻点一下（50ms）——位置几乎不动，朝向变了。

**转向和攻击必须分两拍**：方向键和 Ctrl 如果挨着发出去（间隔不到 20ms），游戏会在同一帧里一起处理，往往按「转身前」的朝向出招，看着就是朝着反方向挥刀。所以转向的那一轮只转身、不出手，等 130ms（`TURN_SETTLE_MS`）让游戏把朝向渲染出来，下一轮才按 Ctrl。

朝向是「记住」的，不是每帧都读（游戏里读不到朝向）。这几种情况会主动作废，下一次攻击前重新转身：刚开挂机、重新拿回窗口焦点、人物定位丢失、血量读到 0（死亡复活）。

范围带的纵向位置是按实测锚定的：**这个游戏把名字牌画在角色脚下**，16px 高的牌子对应约 60px 高的人物，脚底离牌顶约 8px。所以带宽画在「牌顶往上 60px」这一段（跟着牌子高度等比缩放），上边线在头顶上方一点、下边线在脚底，不会像早期版本那样整条压到脚底下的平台上。手机 `/m` 的快照里也是同一个位置。

### 按键出口：硬件 CH9329F（默认）或软件注入

按键不是只有一条路，`bot.Sender` 管着两个出口，面板「按键出口」那行切换：

| 模式 | 走什么 | 对游戏来说 |
|---|---|---|
| `auto`（默认） | 有小板用小板，没有就软件 | 尽量用硬件 |
| `hid` | CH9329F：串口 → USB HID | **真实 USB 键盘报文**，没有注入标记 |
| `soft` | `SendInput` + 扫描码 | 带 `LLKHF_INJECTED`，走 DirectInput 的游戏可能无视、反外挂能认出来 |

硬件那条路在 `webui/hidinput.py`，几件事值得记：

- **键盘帧是全量状态，不是增量。** `57 AB | 00 | 02 | 08 | [控制键位图, 00, 键码1..6] | 校验和`，每一帧描述的是"键盘现在是什么样"。所以同时按住右方向 + 喝药必须塞进同一帧；松开就是发一帧不含该键的；**少发一次就卡键**（角色一直跑）。`HidKeyboard` 维护一个 `_down` 集合，每次变化重拼整帧。
- **串口 9600 8N1，一帧 14 字节约 15ms。** 所以 `_tap` 的 55ms 实际按住约 85ms（两次写各 15ms + sleep）。够游戏识别，也不至于让角色多走。
- **端口是独占的。** 服务器一启动就占住 COM5，这时候再跑 `hidbot.exe`（那个 skill 的 CLI）会打不开串口。要手动用 hidbot 就先把挂机服务停掉。
- **掉线回落。** 拔线/串口被抢时，`Sender` 关掉硬件、切到 `SendInput` 继续跑，并把原因挂在面板上（显示「软件·降级」，鼠标悬停看详情）；每 5 秒重试一次硬件。宁可降级也不让脚本整个哑掉。
- 自动找端口：`hidinput.find_port()` 跳过 ELTIMA/蓝牙虚拟串口，优先 CH343，逐个发 `0x01` 读芯片信息，回 `57 AB` 才算数——不会把别的串口设备当成小板。

**硬件不改变"必须前台"这条。** 真键盘的报文一样进当前焦点窗口，所以闸门照旧。硬件解决的是"按键看起来像不像人按的"，不是"能不能投到后台"。

### 只有游戏在前台才发按键

`_game_foreground()` 每轮检查前台窗口，不是游戏就一轮都不发，并且立刻松开所有按住的键（否则方向键卡在按下状态，角色会一直跑）。这不只是礼貌问题：两个出口都是把按键送进**当前前台窗口**，不等你切回游戏，按键会打进你正在打字的地方。

前台判定用 `win32gui.GetForegroundWindow()` 而不是 `ctypes.windll`：后者默认按 `c_int` 返回，64 位句柄会被截成 32 位，跟 `find_window()` 给的整数永远对不上，闸门就会恒判"不在前台"。

其它几道保险：

- 服务器重启后**不会**自动续跑（`update_cfg({"on": False})`）：上次开着的话，参数留着，开关强制回关。
- 关掉挂机时 `release_all()` 把所有键松开。
- 单轮决策抛异常只松键、记错误，线程继续跑，不会因为一次意外就哑掉。

决策用例在 `tools/test_bot.py`（34 条，用假 sender 跑，不发真按键）：范围内攻击、范围外走近、进范围松键、上下层不打、血低喝药、冷却生效、失焦松键、失焦不重复发抬起、找不到人物不乱按、巡逻换向、配置钳位。

硬件这条路的实测（2026-11-08）：记事本里打 `zz`（硬件）+ `8`（软件注入）= `zz8`，方向键按 3 次光标正好移 3 格、没有连发；游戏里只开拾取跑 3 秒，Z 按下 21 次，`input` 全程是「硬件 COM5」、无错误。

## 人物定位（名字牌模板匹配）

入口就在**血条上方那块空白**里（HP/MP/EXP 左边这一列），没有单独的按钮：

- **没模板时**：那里是一个橙色虚线提示块「⚠ 点这里上传名字牌截图」。点它弹出虚线框，然后 **Ctrl+V 粘贴**（最顺手）、把图**拖进去**（框会变绿）、或**点一下选文件**。图不在提示块上也没关系，整页都能接粘贴和拖入。
- **有模板时**：提示块换成名字牌**缩略图**，右上角一个**红色 ✕** —— 点 ✕ 删掉模板（会二次确认），点缩略图则是换一张。状态文字仍然在右边面板的「人物」行：`0.92 · 已定位 56×18`，`未找到` 变红说明当前画面没认出名字牌。
- **搜索范围**在面板「人物范围」那一行：`整宽 · 8%~90%` + 一个「调整」按钮，见下面「搜索范围」一节。

小图要长条形、只包住名字，别带太多背景，png/jpg/webp 都行。**别用整张游戏截图** —— 那样白字铺满全图，模板变成「整个画面的文字布局」，匹配位置必然乱；服务端会检测并拒掉。

之后后台每帧把这块图在画面里找一遍，命中就在画面上画一个天蓝色的 `ME 0.xx` 标记（名字牌一圈框 + 一条指向人物的箭头）。跟识别开关无关，关掉识别也照样画；手机页 `/m` 的快照里也有。

**删模板只是删模板**：点红 ✕ 之后，标记、分数、框同时归零，找人线程留在原地空转；再粘/拖/传一张图马上接着找，不用重启服务。删完什么都不显示、提示块重新出现，都是预期的 —— 没有模板就没有可匹配的东西。（顺带修了一个坑：以前用一次性布尔标记管线程，线程万一异常退出就再也不会被拉起，看着像「点了清除之后就废了」；现在按 `is_alive()` 判断，随时能自愈。`/api/char` 里的 `thread` 字段能直接看线程是否活着。）

**箭头**：固定从框顶往上指（这套客户端把自己的名字牌画在人物**脚下**，所以箭头朝上是正解）。原来的「朝上/朝下」下拉已经去掉，`/api/char/conf` 的 `dir` 参数留着只为兼容老页面，值一律按 `above` 处理。

### 为什么不能直接拿灰度图做模板匹配

实测同一张名字牌、同一台机器上：模板背景均值 19、画面里那块背景均值 136，直接灰度做 `TM_CCOEFF_NORMED`，真身峰值只有 0.74，而画面里别处的误检能到 0.64 —— 差 0.1，根本分不开。换成梯度幅值也救不了：地面石块和木纹的边缘一样丰富。

真正稳的做法是**只匹配白字笔画**：

1. 模板 → 白字掩码（阈值 + 按外接框裁紧，去掉多余背景）；
2. 每帧 → 白字掩码：`顶帽 = 原图 - 3×3 开运算`。开运算保留大块亮区（云、白墙、地面高光），相减后归零，只剩 1~2px 宽的笔画；
3. 两边都做 σ=1.0 的高斯平滑（把笔画糊到 3~4px 宽），各加 **0.02 的底噪**；
4. 用 `TM_CCOEFF_NORMED` 匹配。

两个参数都是一步步试出来的：

- **σ=1.0 平滑**：不平滑时匹配峰只有 **1px 宽**（x=629 得 0.743，x=630 立刻掉到 0.437），亚像素错位或 JPEG 噪声都能让分数腰斩；平滑后峰变成 ±2px 的平台（0.85 / 0.98 / 0.87），分数从 0.74 升到 0.98。
- **底噪 0.02**：白字图里 99% 是 0（黑），直接 `TM_CCOEFF_NORMED` 时全黑小窗口方差≈0，归一化除出一堆 **1.000 的假峰**（实测 top5 全是 1.000，真身 0.958 排不上）。加底噪后常值窗口的相关系数退回 0，假峰全消失。

为什么不直接用 `TM_CCORR_NORMED`：它不看均值，模板缩到 20px 宽时能量太小，**纯噪声上都能刷到 0.95 分**，光看分数根本分不开。

### 搜索范围（ROI）：只在人物可能出现的那一条里找

人物只可能出现在画面中部的一条横向带里 —— 左右能顶满，上下范围很小（上面是小地图/任务栏，下面是地面与 HUD）。把匹配收窄到这条带，上下 HUD 里那些和名字牌一模一样的白字**天然被排除在外**，候选数量掉一个量级，误匹配和耗时一起降。

**怎么调**：面板「人物范围」→ 点「调整」，画面上会出现一条压暗的搜索带、上下两条天蓝边线和左侧百分比标签：

- 抓**边线**（±14px）单独拖上/下边界；
- 抓**带子中间**整条平移（高度不变）；
- 松手即保存，后端立刻按新范围重找，`ME` 标记当场就能看到效果；
- 点「完成」退出，按 **Esc** 撤回本次调整（写回进来时的值）。

范围按**归一化**百分比存在 `webui/charconf.json`（`"roi": [y1, y2]`），换窗口大小/分辨率不用重调；左右恒为整宽，所以只有一个上下区间。带子最窄 5% 画面高，传反了会自动换过来。

实测（真实帧 + 名字牌模板，1366×768）：

| 范围 | 带内全搜耗时 | 贴到带外的名字牌 |
|---|---|---|
| 整屏 `0~100%` | 79.5ms | 会命中 |
| 默认 `8%~90%` | 47.7ms | 不命中 |
| 收窄到 `38%~70%` | **19.1ms** | 不命中 |

耗时基本按带子高度线性下降（收窄到 32% 高度就是 4 倍速）。跟识别开关、YOLO 推理互不影响：两者各自读缓存帧，模板匹配本来只占 YOLO 的百分之一，这层收窄只是让它更便宜、更准。

### 三级搜索（`find_char`）

新方案杀掉了「框乱跳」：

1. **局部 ±60px**：锁定后只在上帧位置附近找（0.2ms）。逐帧位移一般 < 20px，一定落在里面；
2. **局部 ±200px**：跳跃/瞬移/被击退时兜住，不用回全图重找（避免闪烁）；
3. **带内全搜**：只有连续丢 6 帧才走，而且只在搜索范围（默认 `8%~90%` 高、整宽）里搜。取前 5 个峰，按 `分数 - 距离惩罚 - HUD 惩罚` 排序。

**为什么必须局部优先**：画面左下角 LV 栏里印着同一个名字，白字形状和名字牌完全一样，实测分数 0.84（真身 0.96）。全图直搜时它会一直抢位置 —— 人物一走出画面，框就跳到左下角。现在带内搜索 + 局部优先双重挡着，再加上对 HUD 区（底部 7%、顶部 5%、左右各 9%）额外扣 0.12：`0.84 - 0.24 = 0.60`，低于门限，不会再被选中。判定用的是「扣完惩罚的分」，显示出去的仍是原始匹配分。

### 框级防抖（`chase_char_box`）

局部搜索把位置约束在上一帧附近，但 ±200px 的宽搜半径足够装下另一行同名白字（小队栏、聊天里冒出来的同名字、别人宠物的名字）。一次误匹配就能把框甩出去，下一帧再甩回来 —— 看着就像「标记被别的东西引走了」。所以对**匹配结果**再过三道闸：

| 闸 | 条件 | 行为 |
|---|---|---|
| 死区 | 位移 ≤ 2.5px | 当作没动。匹配峰本来就在原地 ±1px 抖，没有死区框会一直微颤（实测 50 帧里抖 2 帧、幅度 1px） |
| 小位移 EMA | 2.5 < 位移 ≤ 12px | 按 α=0.6 融合，慢走时框比匹配结果稳；实测 7px/帧 的走动平均滞后 3.2px、最大 6px |
| 跳变确认 | 位移 > 90px | **先按住旧框不动**，同一处再连续出现 4 帧（约 0.27s）才承认是真瞬移 |

为什么 90px：15fps 下 90px/帧 = 1350px/s，正常跑动 300~500px/s、坐骑也到不了。传送/被击退那种真瞬移，旧位置会彻底失效，4 帧确认就是 0.27s 延迟，转场本来就在黑屏。

按住期间（`guard > 0`）面板的「人物」行显示「校准中」（橙色），`/api/stats` 的 `char.guard` 是对外可见的计数；`ts` 不续命，按满 `CHAR_LOST_AFTER`（0.6s）会直接把标记收掉，不在旧位置留幽灵框。实测：真身闪断 1 帧 / 3 帧，框一动不动；真身连续消失 6 帧、别处有同款名字牌，第 4 帧才切过去，真身回来再 4 帧切回。

### 尺度

名字牌是 2D UI，同一台机器稳定运行时 1:1 就够；但换窗口大小/分辨率、或者上传的图来自别的分辨率截图，尺度会差几个百分点 —— 差 2% 分数就从 0.98 掉到 0.93，差 8% 直接跳到别处。所以上传时会扫一遍：先 ±12% 细扫（步长 2%），全不行再半分辨率粗扫 0.35~1.65，最后回全图复核。尺度存在 `webui/charconf.json`，重启后仍然记得。

### 实测

用你给的那张 `煎饼1987`（56×20）当模板，在 1368×800 的真实截图上：

| 项目 | 结果 |
|---|---|
| 真身匹配分 | 0.958 |
| 左下角同名文字 | 0.840（扣 HUD 惩罚后 0.60，判不通过） |
| 纯噪声画面 | 0.43，直接判定「没找到」 |
| 换窗口大小（画面缩到 0.877） | 扫出 scale 0.88，定位 1px 内 |
| 跳跃 120px / 260px | 宽搜 / 全图各自接回 |
| 合成 120 帧（背景滚动 + 亮度波动 + JPEG 噪声） | **120/120 帧定位成功，定位误差 0px**，分数 min 0.842 / 均值 0.928 |
| 耗时 | 局部 0.8ms/帧，全图重找 18ms（只在丢失时），尺度扫描 0.6s（只在上传/重标时） |

匹配分低于「人物匹配」滑块（默认 **0.80**）就不算找到，标记消失；滑块可实时调，存在 `webui/charconf.json`。

注意：游戏窗口被别的窗口挡住时，抓到的是挡住它的那个窗口，匹配自然找不到人（页面上的「前置游戏」按钮可以先把游戏抬回前台）。

## 依赖

```bash
pip install mss opencv-python fastapi uvicorn pywin32 numpy scipy
pip install imageio-ffmpeg     # 外网视频用，自带 ffmpeg 可执行文件（不用单独装 50MB 的 ffmpeg）
pip install pyserial           # 挂机走 CH9329F 硬件按键时才需要；没装会自动退到 SendInput
```

CH9329F 小板还需要装 CH343 串口驱动（设备管理器里出现 `USB-Enhanced-SERIAL CH343` 就是好了）。挂机服务会把 COM 口占住，这时 `hidbot.exe` 用不了同一个口。

YOLO 模型文件（`best.pt`、`*_openvino_model/`）不入库，换机器要自己拷。
